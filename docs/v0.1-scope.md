# SheetLab V0.1 Scope

## Product Goal

Build the first usable browser-based sheet music editor prototype. The prototype should prove that a user can create a simple score, see staff notation, choose basic note tools, and prepare the foundation for direct notation editing.

## V0.1 Target Outcome

By the end of V0.1, the app should support:

- Creating a score as `Treble only` or `Grand staff piano`.
- Rendering an empty staff system for the selected score type.
- Maintaining a typed internal score model.
- Loading sample score fixtures for render and playback development.
- Managing editor command state such as duration, note/rest mode, accidental, tempo, and score type.
- Preparing the surface for hover ghost notes and click-to-place notes in later steps.

## In Scope For Steps 1-6

- Project scope documentation.
- React + TypeScript app scaffold.
- Basic app shell with top toolbar, left panel, and central sheet surface.
- Internal TypeScript score model.
- Sample score fixtures for treble and grand staff.
- Editor state for selected tool values.
- Empty staff rendering for treble and grand staff.
- Automated tests for model and fixture behavior where practical.
- Build/type checks after implementation steps.

## Out Of Scope For Steps 1-6

- Click-to-place notes.
- Hover ghost note.
- Playback audio.
- PDF export.
- Save/load file UI.
- MIDI device connection.
- Microphone pitch detection.
- MusicXML import/export.
- Multiple voices on one staff.
- Tuplets, lyrics, ornaments, grace notes, and cross-staff piano notation.

## V0.1 Product Constraints

- One voice per staff.
- Default time signature is `4/4`.
- Default tempo is `96 BPM`.
- Supported durations for the first editor version: whole, half, quarter, eighth, sixteenth.
- Supported score types: `treble` and `grand`.
- Staff rendering can be simple and code-native at first; engraving-perfect layout is not required yet.

## Technical Direction

- Frontend framework: React + TypeScript.
- Build tool: Vite.
- State: local React state first; move to Zustand later if state complexity requires it.
- Rendering: SVG-based staff surface first, leaving a path to VexFlow integration.
- Testing: Vitest for model/fixture tests.
- Future audio: Tone.js.
- Future notation rendering: VexFlow or OpenSheetMusicDisplay depending on editor/import priorities.

## Step Gate Rule

A step is complete only when:

- The intended artifact exists in the repo.
- The step-specific test/check passes.
- Existing checks from previous steps still pass.
- The checkpoint file records the result.
